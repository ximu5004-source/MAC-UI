# MAC UI stability repair — 2026-09-27

Scope: intermittent unresponsive widgets, automatic display-off followed by mouse wake producing partial-screen rendering, Dock primary clicks opening tray menus, and Launchpad horizontal paging. This is a development validation, not a newly packaged release.

## Evidence and repairs

- Existing runtime logs show display changes followed by simultaneous widget liveness reloads and widget-map lock timeouts, including 2026-09-26 12:51. Window creation previously waited for the UI thread while widget maps were locked. Creation, reload and destruction now leave those locks before native dispatch; generations prevent old lifecycle callbacks removing replacement instances.
- Heartbeat registration precedes ping emission, consecutive misses are required, and display/session recovery gets a grace interval. Removed periodic forced critical WebView2 garbage collection, which synchronously waited for the UI thread.
- Display snapshots must stabilize in identity, rectangle and DPI. Transient missing/invalid geometry preserves the last usable layout. Display power-on, resume and mode changes request bounded recovery passes even if display identities are unchanged. Both desktop native bounds and WebView2 controller client bounds are reapplied without page reload or extra DPI scaling.
- Native panel show/hide requests are serialized; stale queued intentions are ignored, failures do not poison the queue. Initial monitor reads cannot overwrite a newer monitor event. Failed zoom updates retain the previous applied zoom and allow later retry.
- Dock activation restores a matching window before considering the tray. Ordinary applications are no longer sent synthetic tray left-clicks. Only known messaging applications use the dedicated background recovery route. Input handlers reject secondary/drag-consumed clicks and suppress browser default context menus.
- Tray hooks preserve protocol version and hidden-state update masks, pack signed multi-monitor coordinates correctly, and enqueue owned icon data before slow decoding/writing. A bounded ordered worker recovers from overflow; no detached worker was added inside Explorer's injected DLL.
- Launchpad uses interruptible horizontal transitions with inert outgoing snapshots; wheel momentum is segmented, rapid page reversal is supported, and reduced-motion bypasses animation. Search/reopen/resize clears stale snapshots. Trigger and placement queues retain the latest intent.

It must preserve topmost/click-through styles and skip DWM setup for child or no-redirection windows. Reapplying dimensions alone is insufficient. [DWM requirements](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmenableblurbehindwindow) and [WebView background API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller2) describe the separate layers.

- Repeated the full frontend tests during diagnosis: 48 passed. This is regression coverage only, not evidence that the native black surface is fixed. Required visual acceptance remains physical display-off/mouse-wake plus repeated cursor entry/exit around Dock.

## Desktop activation/layer follow-up

- The old PID 32048 desktop could have `WS_EX_TOPMOST=false` yet still sit in front of normal applications. During Computer Use activation at approximately 11:11, the read-only probe observed zero visible normal windows above it and 27 below (including minimized/helper windows). The existing timer subsequently lowered it. Thus checking only the topmost style was insufficient; the activation-to-timer interval was a real input-blocking risk.
- External desktop z-order changes are now intercepted in constant time. Activation/position changes request one coalesced UI-thread correction; synchronous window callbacks no longer enumerate every other process. Keyboard activation remains permitted. Cross-thread callers only post the correction, without waiting on native positioning.
- Ordering now follows the actual bounded sibling chain rather than assuming EnumWindows order matches GetWindow predecessors. Minimized, cloaked, empty and known event-only helpers are not counted as drawable applications. The complete stack is checked: a raised Explorer host must not pull the interactive desktop above another app. Invalid snapshots, disappearing anchors or failed verification request a non-activating bottom fallback, and are logged as unverified rather than reported as a successful repair.
- Removed delayed native focus acquisition after file creation. Operation/blur generations, menu-origin tokens and component disposal guard DOM rename focus. Rename completion cannot refocus another operation or an input node for a different path; blur-triggered errors do not steal focus back. Owned context menus can naturally return focus, but the desktop never forces a native activation after asynchronous file I/O.
- Final frontend run: 54 tests passed. TypeScript/Svelte/core checks passed with zero Svelte errors/warnings. Main Rust unit tests: 64 passed. Utilities: 36 passed, including the 120 permutations of the desktop/host/application ordering model. These model results are not substitutes for native input testing.
- At 11:20:17, debug PID 31528 started with log `target/debug/desktop-layer-20260927-112017.stdout.log`. All six widgets reached Ready; guard installation and first timer tick were confirmed. At 11:21:10–12, twenty read-only samples during/after real desktop activation all showed `desktop_topmost=false` and zero normal windows below the desktop. Added a once-only subscriber to the existing hook dispatcher for Show, Uncloaked, MinimizeEnd and Foreground. It only filters and posts the already-coalesced request; no new native hook, full enumeration inside a hook callback, high-frequency location subscription or cross-thread UI wait was added.
